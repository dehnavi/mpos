# Planning Rules

MPOS planning artifacts form a strict hierarchy:

```
Roadmap (planning/roadmap.md)
  └─ Epic (planning/epics/EPIC-NNN-*.md)
       └─ Story (planning/stories/STORY-NNN-*.md)
            └─ Task (tasks/<status>/TASK-NNN-*.md)

Sprint (planning/sprints/SPRINT-NNN-*.md)
  └─ references Stories and/or Tasks for that iteration
```

## 1. Relationships

- Every **Story** must set `epic:` in its frontmatter to a valid `EPIC-NNN` ID.
- Every **Task** must set `story:` to a valid `STORY-NNN` ID. `epic:` is optional on a
  task (it can be derived from the story) but if present must match the story's epic.
- A **Story** or **Task** may set `sprint:` to a valid `SPRINT-NNN` ID once scheduled.
  Unscheduled work has no `sprint:` field (or an empty value).
- `planning/roadmap.md` lists every Epic and its target milestone/phase. An Epic that
  exists on disk but is not referenced from the roadmap is a **drift** finding
  (see [conflict-rules.md](conflict-rules.md)).

`mpos conflict scan` reports, as **warning** or **critical** depending on severity:

- A Story whose `epic:` does not resolve to an existing Epic file → **critical**.
- A Task whose `story:` does not resolve to an existing Story file → **critical**.
- An Epic with zero linked Stories → **warning** ("epic has no stories").
- A Story with zero linked Tasks and `status` is not `backlog` → **warning**.

## 2. Status lifecycles

### Epic (`type: epic`)
`draft` → `planned` → `active` → `done` (or `cancelled` from any state)

### Story (`type: story`)
`backlog` → `ready` → `in-progress` → `in-review` → `done` (or `blocked` from
`in-progress`/`in-review`, returning to `in-progress` once unblocked)

### Task (`type: task`)
`backlog` → `active` → `done` (or `blocked` from `active`).
**The task's `status` field must always equal the name of the directory it lives in**:
`tasks/backlog/`, `tasks/active/`, `tasks/blocked/`, `tasks/done/`. `mpos task move`
performs both the file move and the frontmatter update together — never do one without
the other.

### Sprint (`type: sprint`)
`planned` → `active` → `completed` (or `cancelled`). Only one sprint should be `active`
at a time; `mpos sprint plan` warns if a second sprint is activated while another is
already active.

### Decision (`type: decision`)
`proposed` → `accepted` (or `rejected`). An accepted decision may later be
`superseded` by a newer ADR — when this happens, add a `related:` link from the new ADR
to the old one, and update the old ADR's status to `superseded`. Never delete a
superseded ADR.

### Change Request (`type: change-request`)
`pending` → `approved` (or `rejected`) → `applied`.

### Change Report (`type: change-report`)
Generated by `mpos change report` after an update is applied. Status is always `final`.
Change reports are **never edited by hand** after creation.

## 3. Sprints

- A sprint document lists the Stories/Tasks planned for that iteration under
  `## Scope`, each as a link plus its current `status` (kept in sync manually or via
  `mpos sprint plan`, which re-reads linked items' frontmatter).
- `mpos sprint plan --sprint SPRINT-NNN` assigns selected backlog Stories/Tasks to the
  sprint by setting their `sprint:` field and adding them to the sprint's `## Scope`
  section — it does not change their `status`.
- Capacity/velocity notes belong in `## Capacity & Velocity`, not in the roadmap.

## 4. Roadmap

`planning/roadmap.md` is a **living index**, not a planning document in its own right:

- `## Milestones` — ordered list of milestones/phases, each linking to the Epics that
  belong to it.
- `## Epic Index` — a table of all Epics with `id`, `title`, `status`, and milestone.
- The roadmap is regenerated incrementally by `mpos plan epic create` (appends a row) —
  manual edits to prose sections (e.g. milestone descriptions) are preserved.

## 5. Scope changes

If implementation work expands beyond what a Story/Task describes:

1. Update the Story/Task's `## Description` or `## Acceptance Criteria` via
   `mpos doc update` (section-level — do not silently rewrite).
2. If the change is significant enough to affect sprint scope or estimates, run
   `mpos change request` to record why, then `mpos sprint plan` to reflect the new
   scope.
3. If neither happens, `mpos conflict scan` will flag **"scope expansion without
   planning update"** as a warning once it detects new `[BUSINESS_RULE]` or acceptance
   criteria entries added after the story's `sprint:` was set, with no corresponding
   change request.
